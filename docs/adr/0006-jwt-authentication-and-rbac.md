# ADR-0006: JWT(Access/Refresh)와 Redis 기반 인증, 역할별 접근 제어

- 상태: Accepted
- 날짜: 2026-11-03
- 이슈: #142

## 배경

`/api/v1/**` 전체가 `permitAll`이라 인증과 인가가 없었다. 로그인 API는 회원 정보만 돌려줄 뿐 토큰을 발급하지 않았고, 감사 필드(`created_by`)는 항상 `1L`이었다.

## 결정

**인증**
- 로그인하면 Access Token과 Refresh Token을 발급한다.
- Access Token은 HS256 서명 JWT다 (`sub`=회원 ID, `role` claim, 기본 30분). 서버에 상태를 저장하지 않는다. 검증은 Spring Security OAuth2 Resource Server가 한다.
- Refresh Token은 서명하지 않는 불투명 랜덤 값(32바이트)이다. Redis에 SHA-256 해시를 키로 회원 ID를 저장하고 TTL(기본 14일)을 둔다. 원문은 저장하지 않는다.
- 재발급할 때마다 Refresh Token을 회전한다. 조회와 동시에 삭제(`GETDEL`)해서 한 토큰은 한 번만 쓸 수 있다. 재발급 시 회원을 다시 조회하므로 역할 변경은 다음 재발급부터 반영된다.
- 같은 계정의 여러 로그인 세션은 서로 독립적이다. 로그아웃은 제출한 Refresh Token 하나만 폐기한다.
- HS256 비밀키는 환경변수 `JWT_SECRET`으로 받는다 (기본값 없음, 32바이트 미만이면 기동 실패). 이 애플리케이션이 발급과 검증을 모두 하므로 대칭키로 충분하다.

**인가**
- `SecurityConfig` 한 곳에서 URL과 HTTP 메서드별로 역할을 지정한다. 규칙에 없는 경로는 기본적으로 거부한다.
- 규칙 표는 `AuthorizationMatrixTest`에 있고, 이 표가 실제 컨트롤러 매핑 전체와 정확히 일치하는지 검사한다. 새 엔드포인트의 권한을 빠뜨리면 CI가 실패한다.

**감사자**
- `created_by`와 재고 이력의 행위자는 요청한 로그인 사용자의 회원 ID다. 인증 정보가 없으면 시스템 감사자 `0`이다.
- `@Async` 실행기는 호출한 스레드의 보안 컨텍스트를 전달한다. 발주 확정 후 비동기로 일어나는 창고 배정과 출고 생성도 확정한 사용자가 행위자로 기록된다.

## 결과

- Access Token은 만료 전에는 취소할 수 없다. 즉시 차단이 필요하면 만료 시간을 줄이거나 차단 목록을 도입해야 한다.
- Redis가 필요하다. Redis 장애 시 로그인과 재발급이 실패한다. 이미 발급된 Access Token으로 하는 API 호출은 영향이 없다.
- 시스템이 스스로 시작하는 작업(예약 작업 등)은 보안 컨텍스트가 없어 행위자가 `0`이 된다. 재고 이력의 `member_id`는 `member`를 FK로 참조하므로 이런 작업을 만들 때는 시스템 회원을 정하고 그 회원으로 실행해야 한다.
- 담당 창고나 소속 가맹점 단위의 데이터 접근 제어는 아직 없다. 역할 단위로만 제한한다. 로그인 시도 횟수 제한도 없다.
- 기존 `POST /api/v1/members/login`은 제거되었고 `POST /api/v1/auth/login`으로 대체되었다.
