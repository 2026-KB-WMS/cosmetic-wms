# ADR-0005: 트랜잭션 격리 수준을 READ COMMITTED로 설정

- 상태: Accepted
- 날짜: 2026-11-03
- 이슈: #140

## 배경

통합 테스트를 H2에서 MySQL(Testcontainers)로 전환하자, 동시 입고 수령 시 DOCKING 구역 점유량 갱신이 유실되는 문제가 드러났다. 50건을 동시에 수령하면 모두 성공으로 응답하지만 `section.current_capacity`는 500이 아니라 50이었다.

창고 행에는 `PESSIMISTIC_WRITE` 락을 걸지만, 같은 트랜잭션이 락 이전에 일반 조회로 스냅샷을 만든다. MySQL 기본 격리 수준(REPEATABLE READ)에서는 이후의 일반 조회(`refresh`, 하위 `section`의 지연 로딩)가 그 스냅샷 기준의 오래된 값을 읽는다. 오래된 값을 바탕으로 계산해 저장하므로 다른 트랜잭션의 갱신을 덮어쓴다. H2 기본 격리 수준에서는 이 현상이 없어 기존 테스트가 통과하며 문제가 가려져 있었다.

## 결정

커넥션 풀의 격리 수준을 `READ COMMITTED`로 설정한다 (`spring.datasource.hikari.transaction-isolation`). 격리 수준만 바꿨을 때 동시성 테스트가 통과하는 것을 반복 확인했다.

## 결과

- 락 이후의 일반 조회가 최신 커밋 값을 읽으므로 `PESSIMISTIC_WRITE`와 조합해 갱신 유실이 사라진다.
- phantom read가 허용된다. 이 시스템은 행 단위 비관적 락으로 정합성을 지키므로 영향이 작다. 대신 gap lock이 줄어 Deadlock 위험이 낮아진다.
- 격리 수준은 모든 연결에 적용된다. 특정 유스케이스만 다른 수준이 필요하면 `@Transactional(isolation = ...)`을 쓰되, 이미 시작된 바깥 트랜잭션에 참여하는 경우에는 무시된다는 점에 주의한다.
- 운영 DB에서 계정/서버 수준으로 다른 격리 수준을 지정했다면 이 설정이 우선한다. 배포 전에 확인한다.
- 테스트는 `application.yaml`의 이 설정을 그대로 쓴다. 테스트만 격리 수준을 바꾸면 운영과 다른 조건에서 통과하게 되므로 하지 않는다.
